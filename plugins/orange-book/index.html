这本书讲什么

DBX 把 SSH 终端、S3 文件浏览、Kafka、Kubernetes 这类能力做成可选安装的 .dbxp 插件，基础安装包保持在 20 MB 左右。截至 2026 年 10 月 1 日，官方商店已上架 37 个插件。

第 1 章 · Overview

全景：DBX 的三层扩展模型

DBX 能连 90 多种数据源，以「插件」形式安装的只是其中一层。先分清三种扩展方式各自落在哪里，后面的设计才说得通。

1.1构建期声明：YAML 编进二进制

plugins/connection-types/*.yaml 是 DBX 所有连接目标的注册表，覆盖 SQL 数据库、文档与向量库、键值和配置服务、消息队列、MQTT 与通用 JDBC。每个描述文件定义稳定的 dbType、生成的 Rust 枚举成员、运行模式（原生或 Agent）、默认端口、连接表单种类和一组能力开关。dbx-types/build.rs 在编译时读取它们生成 DatabaseType 枚举，前端类型由 pnpm generate:connection-types 同步生成。

plugins/connection-types/etcd.yaml（节选）
schemaVersion: 1
dbType: etcd
rustVariant: Etcd
label: etcd
runtimeMode: agent        # 由 Agent 驱动进程执行
agentKey: etcd
defaultPort: 2379
capabilities:
  queryExecution: true
  metadataBrowse: false
  driverManagement: true

plugins/dialects/*.yaml 描述 SQL 方言的类型目录、DDL 模板与元数据规则，由 dbx-sql/build.rs 读取；plugins/mappings/ 存放跨方言的类型映射规则。

这一层没有独立进程，也不单独分发，改动随 DBX 一起编译发布，需要向 t8y2/dbx 提 PR。它适合「协议与已有实现兼容的新产品」：多数情况下加一个目录条目和图标就够了，只有协议、认证、元数据或界面流程不同时才需要写代码。

1.2Agent 驱动：独立进程里的数据库连接器

agents/ 下是用 Java（JDBC）和 Go（原生驱动）写的驱动代理，覆盖 DB2、Snowflake、Hive、Neo4j、TDengine、达梦等 40 多种目标。每个 Agent 是独立进程，经 stdin/stdout 以 JSON-RPC 2.0 与 DBX 通信。驱动在首次使用时从驱动商店下载，Java Agent 需要的 JRE 21 由 DBX 自动下载和管理。

Agent 与 YAML 一样由主仓库维护和发布；数据库厂商的 JDBC 驱动 JAR 由用户在本机导入，不提交到任何 Git 仓库。早期的 plugins/jdbc（Manifest v0 格式的 JDBC Sidecar）在迁移到 Manifest v1 期间保留。

1.3.dbxp 运行时插件：本书的主角

任何开发者都可以在自己的仓库里写插件，产物是一个 .dbxp 包。插件能贡献连接类型、工作台界面、虚拟文件系统、右键菜单、结果视图、命令和 AI 工具，覆盖面远超数据库驱动：商店里的 SSH 终端、S3 浏览器、Kafka 控制台、Kubernetes 管理都是这样做出来的。

平台契约由四个版本号描述：Manifest v1（包的声明格式）、Host API 1.x（宿主开放给插件的能力，当前 1.4.0）、Sidecar 协议 v1（原生后端的线协议）和 Catalog v1（商店目录格式）。可选插件不进入 DBX 基础安装包，装多少插件只影响本机插件目录的大小。

第 2 章 · Anatomy

插件包剖析：.dbxp 与 Manifest v1

.dbxp 是一个规则更严格的 ZIP。把它拆开，信任链和声明式契约就都摆在眼前。

2.1包里有什么

vendor.example-1.0.0-darwin-arm64.dbxp
vendor.example-1.0.0-darwin-arm64.dbxp    # ZIP 容器
├── manifest.json                          # 运行时契约
├── checksums.json                         # 其余每个文件的 SHA-256
├── signature.json                         # 仓库签名；只有开发安装可以缺省
├── bin/darwin-arm64/example-plugin        # 原生 Sidecar（可选）
├── assets/plugin.svg                      # 插件与贡献点图标
└── ui/
    ├── index.html                         # 沙箱 UI 入口（可选）
    └── assets/…

文件名约定为 <id>-<version>-<target>.dbxp。target 取 darwin-arm64、darwin-x64、linux-x64、linux-arm64、windows-x64、windows-arm64 之一；纯前端插件用一个 universal 包。安装时 DBX 先找与当前平台完全匹配的包，找不到才回退到 universal。

安装后，包被解压到插件仓库目录，并按版本分开存放：

DBX 数据目录（安装后）
<DBX 数据目录>/
├── plugins/
│   ├── .install.lock                 # 安装、回滚、卸载、信任库变更共用的文件锁
│   ├── .repositories.json            # 已启用的商店仓库
│   ├── .trust/keys.json              # 用户信任的自定义仓库公钥
│   └── vendor.example/
│       ├── versions/1.0.0/           # 解压后的版本，安装后不再改动
│       ├── versions/1.1.0/
│       └── activations/              # 激活记录：版本、上一版本、包 SHA-256、来源
└── plugin-data/vendor.example/       # 插件自己的数据，升级和卸载后都保留

激活记录按序号递增，以临时文件写入后再原子改名。它决定当前生效的版本，并记下上一个可用版本作为回滚目标，同时记录包的 SHA-256 和来源（商店仓库、发布者、签名 Key ID、安装方式）。第 6 章会用到这份来源记录。

2.2Manifest v1

manifest.json 是运行时契约，位于包根目录。下面是一个纯前端插件的最小 Manifest：

manifest.json
{
  "$schema": "https://raw.githubusercontent.com/t8y2/dbx/main/plugins/manifest.schema.json",
  "manifest_version": 1,
  "id": "com.example.files",
  "name": "Example Files",
  "version": "0.1.0",
  "publisher": "example",
  "description": "Browse files from an example service.",
  "icon": "assets/plugin.svg",
  "source": "https://github.com/example/dbx-plugin-files",
  "engines": { "host_api": "1" },
  "permissions": [],
  "entrypoints": { "ui": { "root": "ui", "entry": "ui/index.html" } },
  "contributions": [
    { "type": "workbench", "id": "com.example.files.main", "label": "Files" }
  ]
}
字段必需说明
manifest_version是固定为 1
id是全局唯一，发布后不要改；只能用小写字母、数字、. _ -，最长 128
name / descriptionname 必需显示名称与说明，可被 localizations 覆盖
version是语义化版本；同 ID 同版本的正式包不能覆盖安装
publisher是发布者标识，商店据此认定归属；它不是签名密钥的持有者
engines是host_api 必填（如 ^1.4），dbx 可选（如 >=0.6.0）
permissions否最小权限集合，见 6.5 节
entrypoints否ui：root + entry；backend：executable + transport + protocol_versions
contributions否八种贡献点，见 2.3 节
icon / source / homepage否包内图标路径、源码与主页地址；随包签名，安装后离线可见
localizations否按 locale 覆盖名称、说明、贡献点与表单文案
  • plugins/manifest.schema.json 只是编辑器辅助，真正的校验在运行时：ID、语义化版本、engines 范围、权限白名单、贡献点之间的引用、表单字段类型与绑定、入口路径，以及当前平台的可执行文件是否存在。
  • 不接受未声明的顶层字段，会报 Plugin manifest contains unknown top-level field(s)。表单 picker、组合条件、mcp 贡献点这类后加的字段，会让旧版 DBX 无法解析整个 Manifest，依赖它们时要把 engines.dbx 提到对应版本。
  • 路径一律相对包根目录：不能以 / 开头，不能含 ..、反斜杠或 //。ui.entry 必须落在 ui.root 内，root 为 ui 时 entry 写 ui/index.html。
  • 原生插件的 backend.executable 指向当前平台的可执行文件，所以每个平台各打一个包；transport 默认 stdio-jsonl，需要二进制帧时用 stdio-framed。

2.3八种贡献点

贡献点（contribution）是插件向 DBX 界面「挂」东西的唯一方式。DBX 不会为某个插件增加专用的前端分支，所有界面入口都由这八种声明驱动：

类型作用依赖
connection-provider让插件出现在「新建连接」中。表单由插件声明、DBX 渲染；测试、连接、断开由 Sidecar 实现（第 5 章）后端
workbench在普通 DBX 标签页里打开沙箱 UI，可附带最多 5 条 AI 推荐问题UI
filesystem-provider声明 URI scheme 与读写能力，由 DBX 的通用文件管理器展示；后端实现 filesystem/list、read 等方法后端
context-menu在侧边栏的连接或表右键菜单里加一项：可声明式打开工作台，也可调用后端或动态生成子菜单宿主 后端
result-view在查询结果工具栏加一个按钮，把结果快照（最多 500 行）交给插件 UIUI

2.4本地化

localizations 的键是 locale（如 zh-CN、en），可以覆盖插件名称、说明，以及每个贡献点的 label、description、表单字段和按钮文案。DBX 先找完全匹配的 locale，再找基础语言，最后回退到 Manifest 中的默认文本。插件 UI 内部的文字不在其中，要根据 dbxPlugin.locale 自行翻译。

manifest.json · localizations
"localizations": {
  "zh-CN": {
    "name": "示例文件",
    "contributions": {
      "com.example.files.connection": {
        "label": "示例服务",
        "fields": { "token": { "label": "访问令牌" } }
      }
    }
  }
}

第 3 章 · Runtime

运行时架构：宿主、Sidecar 与沙箱 UI

一个插件运行时最多分成两半：跑在沙箱 iframe 里的 UI，和跑在独立子进程里的原生 Sidecar。DBX 宿主站在两者中间，每一次调用都要经过它。

3.1一次调用经过哪些组件

以官方示例 hello-workbench 为例：用户在工作台里点按钮，UI 调用 dbxPlugin.invoke("hello/greet")，请求穿过桥、Tauri 命令和 Rust 核心，写进 Sidecar 的 stdin，结果再沿原路回到 UI。点「播放」看一个请求走完全程。

  1. UI 发起调用。SDK 注入的 window.dbxPlugin.invoke(method, params, { timeoutMs }) 把请求通过 postMessage 发给父窗口。
  2. 桥校验后转交。Host Bridge 只接受来自本 iframe 窗口、带正确协议标记的消息，检查载荷大小与权限，再以插件自身的 ID 调用 Tauri 命令 invoke_plugin。UI 没有办法指定别的插件。
  3. 找到或拉起进程。PluginHost 查找这个插件的会话；还没启动就按需拉起 Sidecar 并完成握手（3.2 节）。同一插件的所有标签页共用一个进程。
  4. 分配 id、开始计时。SidecarSession 分配一个数字请求 id，登记等待者。默认超时 30 秒；UI 传入的 timeoutMs 被夹在 1–120000 毫秒。
  5. 写入 stdin。一行 JSON-RPC 请求，或一个 framed 帧。
  6. 插件处理。SDK 的 PluginServer 把请求交给工作线程池，你的 handle() 按方法名分发；需要访问远端时，连接 runtime.host:port。
  7. 经 stdout 返回。响应带着同一个 id，会话据此唤醒等待者，结果沿原路回到 UI，Promise resolve；出错时 reject。
  8. 事件单独广播。Sidecar 随时可以发 JSON-RPC 通知（没有 id）。宿主按插件 ID 广播，只有声明了 host.events 的工作台会收到。

3.2启动与握手

Sidecar 不随 DBX 启动。第一次有请求需要它时（测试连接、打开工作台、调用方法），PluginHost 才拉起进程，工作目录是该版本的安装目录，stdin、stdout、stderr 全部接管为管道，进程句柄被释放时子进程随之结束。随后宿主发出 plugin/initialize，Sidecar 必须在 30 秒内应答。

下面用 hello-workbench 走一遍「连接一个需要二次验证的插件连接」的完整时序。点击任意一行，或用按钮逐条查看消息的真实内容。

Sidecar 启动时，宿主注入这些环境变量：

环境变量值
DBX_PLUGIN_IDManifest 中的 id
DBX_PLUGIN_VERSIONManifest 中的 version
DBX_APP_VERSIONDBX 版本，例如 0.6.29
DBX_HOST_API_VERSION1.4.0
DBX_PLUGIN_PROTOCOL_VERSION1
DBX_PLUGIN_DATA_DIR<数据目录>/plugin-data/<id>：跨版本保留，所有 Sidecar 实例共享；宿主不预先创建，首次写入前自己建目录。Go SDK 提供 DataDir() 与 EnsureDataDir()
握手失败

Sidecar 返回的 protocolVersion 必须是 1，plugin.id 和 plugin.version 必须与 Manifest 完全一致，否则宿主结束进程并报 Plugin backend identity '…' does not match manifest '…'。这能拦下「包里的可执行文件其实属于别的插件或别的版本」这类打包错误。用 SDK 时，把 PluginMetadata::new 的版本写成 env!("CARGO_PKG_VERSION")，并让 Cargo 版本与 Manifest 保持一致。

3.3进程生命周期

  • 一个插件一个进程，不按标签页启动。插件自己维护会话表，例如 hello-workbench 用 connection.id 保存已连接的会话。
  • stdout 一旦出现无法解析的 JSON、缺少 "jsonrpc": "2.0"、既无 id 也无 method 的消息，或单条消息超限，宿主让所有挂起的请求失败，终止进程，状态变为 Exited。
  • stderr 的每一行都以 [plugin:<id>] 为前缀写入 DBX 日志。诊断信息往这里写，不要写 stdout。
  • 有连接或操作在用时，升级、回滚、卸载会被拒绝，例如 Plugin update blocked by active connections: …。替换或卸载前，DBX 先拆掉插件持有的连接池；还有已保存连接引用该插件时不能卸载。
  • 卸载先把插件目录原子地改名移入 .trash，这一步就算提交，之后才物理删除。删除失败（例如杀毒软件占用了刚解压的文件）只记警告，下次安装或卸载时再清理，插件目录不会停在半删状态。

第 4 章 · Protocol

通信协议：JSON-RPC、帧与 Host API

宿主与 Sidecar 之间只有一对 stdio 管道，沙箱 UI 与宿主之间只有 postMessage。两条通道都有固定的格式、方向规则和上限。

4.1Sidecar 协议 v1

所有消息都是 JSON-RPC 2.0。stdout 只能写协议消息，日志一律写 stderr。一条管道上同时跑着五种消息，靠 id 的有无和类型区分方向：

方向形态id例子
宿主 → Sidecar请求数字plugin/initialize、connection/connect、filesystem/list、自定义方法
Sidecar → 宿主响应同一个数字result 或 error
Sidecar → 宿主通知（事件）无hello/progress
Sidecar → 宿主宿主 API 请求（Host API 1.1 起）字符串host/requestUserInput
宿主 → Sidecar对上一行的响应同一个字符串{ "action": "submit", "value": "…" }

旧宿主只认数字 id，看到字符串 id 的帧会直接丢弃而不是报错，所以新能力可以在不改线格式的前提下加进来。只有 host/ 开头的方法才会被当作宿主 API 请求，这个前缀保留给宿主，插件声明的方法不会收到它。

传输方式有两种。stdio-jsonl 是默认值，一行一个 JSON。PTY、SFTP、文件传输这类需要二进制通道的插件用 stdio-framed，每条消息前加 5 字节帧头：

  • 单条 JSON 消息上限 8 MiB，Rust 与 Go SDK 都按此执行。宿主读取 JSONL 行时放宽到 64 MiB，为的是兼容把一整页查询结果写在一行里的旧插件。
  • 二进制帧上限 64 MiB；沙箱 UI 与宿主之间的二进制消息每条最多 8 MiB，以可转移的 ArrayBuffer 传递，不再经过 base64。
  • 宿主支持多个请求同时在途。Rust SDK 默认用 2–16 个工作线程和 256 个任务的队列，可用 worker_threads() 与 work_queue_capacity() 调整；连接和断开要写成幂等的。
  • Rust 与 Go SDK 都支持两种传输：Rust 用 .transport(PluginTransport::Framed)，Go 用 WithTransport(TransportFramed)。Manifest 中的 transport 必须同步改成 stdio-framed，UI 要收发二进制还需声明 host.binary。

4.2反向请求：插件向用户要输入

Host API 1.1 增加了唯一一个由 Sidecar 发起的宿主方法 host/requestUserInput。堡垒机的 keyboard-interactive 验证码、主机密钥确认、多账号选择，都靠它借用 DBX 自己的阻塞对话框，测试连接和真实连接走同一条路。

参数约束
prompt必填，≤ 2000 字符
title · default可选，分别 ≤ 200 与 ≤ 1000 字符
options可选，≤ 8 项，值唯一，每项 ≤ 200 字符
echo默认 false，对话框遮住输入
timeoutSecs夹在 5–600 秒，默认 300
  • 结果只有三种：{"action":"submit","value":"…"}、{"action":"cancel"}、{"action":"timeout"}。只有 submit 带值；cancel 和 timeout 都按「没有答案」处理，失败关闭，不要猜一个值继续。
  • 对话框打开期间，宿主暂停等待它的那次请求的计时（单次请求最多暂停 600 秒），用户慢慢输验证码不会被当成连接超时。
  • 错误码：-32001 没有可用界面（headless、MCP 场景），-32602 参数不合法，-32601 宿主不支持，-32002 该会话已有 4 个提示未关闭。三种情况都要优雅降级，不能一直阻塞。
  • DBX 只回传用户亲手输入的内容，不自动填充、不缓存、不写日志。调用前先确认握手里的 hostApiVersion ≥ 1.1.0，或 host.features 含 host.requestUserInput。目前只有 Rust SDK 封装了这个调用：
Rust · 向用户请求验证码
use dbx_plugin_sdk::{host_client, PluginError, UserInputPrompt};

fn ask_verification_code() -> Result<String, PluginError> {
    let host = host_client().ok_or_else(|| PluginError::new(-32001, "No host UI"))?;
    if !host.supports("host/requestUserInput") {
        // 旧宿主不认识这个方法：明确失败，不要阻塞
        return Err(PluginError::new(-32601, "Host cannot ask for input"));
    }
    let prompt = UserInputPrompt::secret("Verification code (6 digits)").with_title("JumpServer login");
    let answer = host.request_user_input(&prompt)?;
    // cancel 与 timeout 都没有值：失败关闭，不要猜
    answer
        .submitted()
        .map(str::to_string)
        .ok_or_else(|| PluginError::new(-32010, "Login cancelled"))
}

4.4上下文、主题与静态资源

  • 上下文是 JSON 快照。宿主会递归去掉 Vue 的响应式包装，只传 null、布尔、有限数字、字符串、数组和普通对象，UTF-8 编码后上限 2 MiB。Date、Map、Set、BigInt、循环引用和自定义类实例会被拒绝。上下文变化通过 onContext 推送，iframe 不重新加载，UI 状态得以保留。
  • 主题跟随 DBX。宿主把 --color-*、--radius-*、--font-* 设计变量注入文档根元素，并更新 data-dbx-theme；变化经 dbx-plugin-env 事件实时推送。每个沙箱文档还自带一套小型组件样式：dbx-card、dbx-btn、dbx-input、dbx-table、dbx-badge 等。
  • 资源必须打进包里。入口脚本被内联进沙箱文档，其余资源经 dbx-plugin://localhost/<id>/…（WebView2 上是 http://dbx-plugin.localhost/<id>/…）只读访问，限定在 ui.root 内。构建产物要用相对地址：Vite 设 base: "./"，webpack 设 publicPath: "./"；以 /assets/ 开头的绝对路径带不上插件 ID，会 404。不要把 Vite 开发服务器或 CDN 地址写进发行包。
  • 浏览器能力受限。沙箱是不透明源，localStorage 会直接抛异常，改用 host.storage；不要依赖 alert、confirm、prompt，用自己的对话框组件。

第 5 章 · Connection provider

连接提供者：把插件接进「连接」

connection-provider 让插件拥有一个出现在 DBX 连接列表里的连接类型。表单由插件声明、DBX 渲染；保存、Secret 存储和隧道都由 DBX 负责，插件只处理自己的协议。

5.1表单字段与绑定

每个字段用 binding 决定存到哪里：

binding存储位置
name host port username password databaseConnectionConfig 中对应的通用字段；port 必须是 number 类型
configexternal_config[key]，插件自定义的非敏感配置
secretconnection_secrets[key]，存在 config_json 之外；password 类型的字段不写 binding 时默认按 secret 处理
  • 字段类型有七种：text、password、number、boolean、select、radio、textarea。select 和 radio 必须给非空的 options。DBX 在调用插件前就校验必填项和类型，插件收到的是合法的值。
  • 没有填写的可选字段保持缺省，不会变成空字符串或文本 "null"。
  • picker 让 text、password、textarea 字段选择本机文件：桌面端存绝对路径，插件后端同机运行，可以自己读；网页端拿不到路径，改为上传内容（≤ 1 MiB）到声明的 content_field。两种来源互相清除，避免一份过期上传和一个新路径同时存在。
  • visible_when 与 required_when 支持 all_of、any_of、not 组合，最多 8 层、64 个节点。对话框和保存、测试、连接时的校验用同一套求值，不会出现「表单放行、宿主拒绝」。
  • 声明一个 config 字段 connect_timeout_secs，它就成为该插件连接超时的唯一来源：connection/test 和 connection/connect 的截止时间取用户填写的值或默认值，夹在 1–300 秒；不声明则使用连接的通用超时（默认 10 秒）。

5.2生命周期请求

连接的生命周期只有四个固定方法：connection/test、connection/connect、connection/disconnect，以及自定义按钮用的 connection/action。provider 声明了哪些 capabilities，DBX 才会调用对应的方法。参数结构如下：

connection/connect · params
{
  "provider": { "id": "dbx.example.hello.connection", "databaseType": "hello" },
  "connection": {
    "id": "saved-connection-id",
    "db_type": "plugin",
    "plugin_id": "dbx.example.hello",
    "plugin_connection_provider": "dbx.example.hello.connection",
    "plugin_connection_type": "hello",
    "external_config": { "greeting": "Hello" },
    "connection_secrets": { "api_token": "只在后端请求中补齐" }
  },
  "runtime": { "host": "localhost", "port": 22 }
}
  • runtime.host / runtime.port 是经过 SSH 跳板、SOCKS、HTTP 代理之后的最终端点。插件直接连它，不要自己再建隧道。
  • Kafka 这类会在握手后通告更多地址的多端点协议，静态隧道只能转发一个端点。在 provider 上声明 "proxy_route": true，配置了传输层时 DBX 会改为下发 SOCKS5 路由 runtime.proxy，插件经它拨号所有通告出来的端点。代理凭据和 Secret 走同一条通道，不得写日志。
  • 用 connection.id 作为会话表的键，connect 与 disconnect 写成幂等的；后续工作台请求只带 connectionId，由插件在会话表里查找。

5.3自定义按钮

provider 可以在 DBX 的「测试」「保存」「保存并连接」之前加几个自己的按钮，比如「自动发现端点」：

manifest.json · actions
"actions": [
  { "id": "discover", "label": "Discover endpoint", "variant": "outline",
    "when": "create", "requires_valid_form": false, "timeout_ms": 30000 }
]
connection/action · result
{ "success": true, "message": "Endpoint discovered",
  "fieldValues": { "host": "db.internal", "port": 5432 } }
  • DBX 只会调用固定方法 connection/action 并带上 action: { id }，插件不能借按钮触发任意方法名。
  • fieldValues 只能写本 provider 声明过的字段，类型必须匹配，null 表示清空。插件改不了 ConnectionConfig 的其他键，也绕不开 DBX 自己的保存、Secret 持久化和隧道逻辑。
  • when 取 always、create 或 edit；timeout_ms 在 1–120000 之间；只有 requires_valid_form: false 的按钮能在表单未填完时运行。

第 6 章 · Security

安全设计

DBX 的插件安全不押在单一机制上。它把风险拆到几条边界，每条边界有自己的闸门。先看边界，再逐条看闸门，最后说清楚哪些事 DBX 管不了。

6.1信任边界

一个插件同时跨越四种信任等级：DBX 宿主完全可信，持有凭据、连接池和界面；插件的原生 Sidecar 是作者写的原生代码，以当前操作系统用户的权限运行；插件 UI 也是作者写的代码，但被关在沙箱 iframe 里；商店目录、下载的字节、远端服务和 AI 模型的输出都按不可信输入处理。

  1. 安装入口。目录与包都有大小上限；下载的字节必须等于目录声明的大小和 SHA-256；包必须带受信公钥的 Ed25519 签名；包内 Manifest 的 ID、版本、发布者、权限和签名 Key ID 必须与目录一致（6.2、6.3 节）。
  2. 沙箱 UI 与宿主之间。桥只接受来自本 iframe 窗口、带正确协议标记和版本的消息；未声明的权限直接拒绝；载荷不超过 2 MiB；每个调用都绑定到插件自身 ID（6.4 节）。
  3. 沙箱 UI 的网络出口。CSP 默认 connect-src 'none'，只放行 Manifest 声明的最多 8 个 https origin。
  4. 宿主与 Sidecar 之间。握手核对协议版本与后端身份；每个请求有超时；消息有 8 MiB / 64 MiB 上限；输出违反协议就终止进程。
  5. 凭据。Secret 只在生命周期请求里交给 Sidecar，不进 UI 上下文、事件和日志（6.7 节）。
  6. AI 工具。用户在插件中心开启后才暴露；只作用于已打开的连接；未标注只读的工具每次调用都要用户批准（6.8 节）。
  7. 没有闸门的地方。原生 Sidecar 对本机文件、网络和进程的访问，DBX 无法完整约束（6.9 节）。

6.2供应链：从源码到安装

官方商店的流程把四件事分给了不同的机制，它们互相不能替代：

  • 人工审核决定插件能否进入官方目录、能否显示 verified。
  • 目录里的 SHA-256 与大小证明下载到的正是审核时选定的那个文件。
  • Ed25519 仓库签名证明安装的字节就是该仓库审核并发布的字节。
  • 运行时权限与宿主边界限制安装之后插件 UI 能请求什么。

审核挡不住「已批准的下载地址后来被替换」；签名也不代表插件安全或经过审核，它只认证签名者和字节。

  • 公钥随客户端发布。DBX 内置 dbx-store-preview-2026 与 dbx-store-release-2026（当前在用）两把官方公钥，发布构建可以通过 DBX_PLUGIN_MARKETPLACE_TRUSTED_KEYS_JSON 追加轮换用的新公钥。从官方仓库安装时，信任库只包含这些内置公钥，用户自己添加的公钥冒充不了官方包；本地文件安装时，如果用户保存的某个 Key ID 与内置 ID 重名但公钥不同，安装直接失败。
  • 密钥轮换不复用 ID。同一个 Key ID 永远对应同一把公钥。轮换时启用新 ID，先让各版本客户端信任新公钥，再停用旧密钥；泄露的密钥写入 revoked.json。
  • 私钥有人看守。签名工作流运行在需要审批的 GitHub Environment 中（plugin-signing，所有者另有 plugin-signing-owner），签名前重新下载候选包、核对已审核的 SHA-256 与大小、确认包内没有签名并且 Manifest 身份一致，然后签名并生成签名回执。负责开 PR 的自动化 GitHub App 无权读取签名密钥。
  • 发布即不可变。签名后的包上传到 R2，禁止覆盖已有对象；包的任何字节变化都必须发新版本。官方目录主地址是 https://dl.dbxio.com/catalog/index.json，失败时回退到 GitHub 上的 catalog/index.json。
  • 自定义仓库同构。企业或私有仓库用 dbx-plugin keygen 生成自己的仓库密钥，用户在插件中心「自定义仓库信任」中添加 Key ID 和 Base64 公钥。公钥应通过独立于下载包的渠道获取。

6.3安装闸门：十道检查

从商店安装一个插件，要依次通过下面十道检查，任何一道失败都会中止安装，插件目录保持原状。左侧选择一种攻击或失误，看它在哪一道被拦下，以及 DBX 报出的真实错误信息。

6.4沙箱 UI：iframe 里能做什么

工作台以 srcdoc 加载进 sandbox="allow-scripts" 的 iframe。没有 allow-same-origin，文档就是不透明源：拿不到父页面的 DOM、Cookie 和本地存储，也没有 Tauri 对象。宿主在文档头部注入下面这条 CSP（<asset> 是插件资源协议的源）：

注入的 Content-Security-Policy
default-src 'none';
script-src 'unsafe-inline' blob: <asset>;
style-src 'unsafe-inline' blob:;
img-src data: blob: <asset>;
font-src data: blob: <asset>;
connect-src 'none';                 # 声明 host.network:https://… 后改为这些 origin
media-src data: blob: <asset>;
  • 网络。host.network:https://host[:port] 只接受 https、不带路径、通配符或令牌，最多 8 个，重复即报错。声明的 origin 会出现在 connect-src 里，审核者一眼能看出 UI 会访问哪些服务；请求仍受目标服务的 CORS 约束。这条权限只约束 UI，不是 Sidecar 的防火墙。
  • 消息。桥只处理 event.source 正是本 iframe 窗口、带有约定的来源标记和桥协议版本的消息，请求结构逐字段校验，JSON 载荷超过 2 MiB 直接拒绝。
  • 身份。所有后端调用都以桥自身绑定的插件 ID 发出。插件 UI 不能指定别的插件，也就调用不了别的插件。
  • 权限。需要权限的 API 在桥里先检查 Manifest 是否声明，未声明报 Plugin has not declared permission '…'。涉及数据的 API 到了后端还会再查一次。
  • 节流。每个工作台最多 2 个下载、4 个数据查询同时进行；读剪贴板至少间隔 1 秒，最近 200 次读取留有审计记录。

6.5权限：最小授权

权限只约束「宿主替插件做的事」。下表列出每个权限允许什么、绝不允许什么。商店目录里登记的权限必须与包内 Manifest 完全一致，所以新增权限只能通过一个重新审核的新版本。

权限允许不会允许
host.events工作台接收自己 Sidecar 的事件接收其他插件的事件
host.binary与自己 Sidecar 之间的二进制通道（需 stdio-framed，UI 侧每条 ≤ 8 MiB）与其他插件或其他进程交换数据
host.workbench打开本插件的其他工作台、执行本插件声明的命令打开其他插件的界面

6.6读数据要用户同意：host.data:read

  1. UI 调用 queryData，桥先确认 Manifest 声明了 host.data:read，否则直接拒绝。
  2. 桥查询这对（插件，连接）是否已有授权。没有就弹出宿主对话框，写明插件名和连接名。无法弹窗的宿主一律拒绝，不会静默授权。
  3. 用户同意后，授权持久化到 app_settings.plugin_data_grants，显示在插件中心「已安装」的该插件下，可以随时撤销；拒绝会在本次工作台会话内记住，插件无法反复弹窗。卸载插件会同时删除它的授权。
  4. 后端每次调用都重新检查 Manifest 权限和授权。授权被撤销后返回以 PLUGIN_DATA_ACCESS_NOT_GRANTED 开头的错误，下一次查询重新征求同意。授权检查先于连接解析，未授权和连接不存在看起来一样，插件无法借此探测连接是否存在。
  5. SQL 必须是单条语句，并被 DBX 的 SQL 风险分类器判为只读，这和 MCP 只读模式、AI Agent 用的是同一道闸门。写入、DDL、SELECT … FOR UPDATE、多条语句和 USE 切换数据库都会被拒绝；只服务已打开的 SQL 连接，Redis、MongoDB 等不提供这项能力。
  6. 结果有上限：默认 500 行、最多 5000 行，序列化后不超过 8 MiB，超时夹在连接自身超时与 60 秒之内。

6.7Secret 不越界

  • 声明为 secret 的字段从连接 JSON 中移除，存进 DBX 的 Secret Store，config_json 只留占位。
  • 只有 Sidecar 的生命周期请求（test、connect、disconnect、action，以及 AI 工具调用携带的 lifecycle）能拿到补齐 Secret 的连接。工作台上下文只有连接 ID、provider ID 和连接类型；右键菜单交给后端的连接摘要只有 id、dbType、name、database。
  • 云同步快照里的 Secret 一律是脱敏占位。只有用户设置了同步口令，Secret 才以加密载荷进入同步数据，否则留在本机。
  • 插件自己也要守规矩：不要把密码、Token、私钥放进 config 字段、工作台上下文、事件、错误信息或日志。开发宿主 dbx-plugin dev 把凭据以明文存在 .dbx-dev/，这个目录必须加入 .gitignore。

6.8AI 工具的闸门

带原生后端的插件可以实现 mcp/tools 与 mcp/call，把工具交给 DBX 内置的 AI 助手。宿主在中间加了这些约束（crates/dbx-core/src/ai/plugin_tools.rs）：

  • 显式加入。只安装不会暴露任何工具，用户要在插件中心「已安装 → 内置 AI 工具」里开启。Manifest 的 mcp 贡献点写 ai_tools: false 可以彻底退出；外部 dbx MCP 服务器只暴露声明了 external_tools: true 的插件，并且还受全局 MCP 连接白名单约束。
  • 只用已打开的连接。模型看到的 schema 里去掉了 connectionId，由宿主注入绑定的连接；打开了多个连接时，模型只能通过附加的 dbx_connection 参数在其中选择。
  • 默认要批准。只有标注 annotations.readOnlyHint: true 的工具直接执行，其他每次调用都暂停，向用户展示将要转发的完整参数，5 分钟无人应答视为拒绝。这道确认防的是模型误操作和提示注入，挡不住一个本身就恶意的插件，所以插件自己的只读开关、二次确认仍然必要。
  • 有边界。工具名暴露为 <前缀>__<工具名>，schema 被收敛到各家模型都接受的子集；每个插件最多 64 个工具、总计 96 个；发现超时 8 秒、单次调用 120 秒；结果先截断到 200,000 字符供界面展示，交给模型前还会再压缩。内置 Agent 把工具输出当作不可信数据，插件应返回事实而不是指令。

6.9DBX 管不了的部分

原生 Sidecar 以当前操作系统用户的权限运行。仓库签名证明的是「哪个仓库审核并发布了这些字节」，它既不是操作系统沙箱，也不证明作者无害。DBX 目前无法完整约束原生进程对文件系统和网络的访问。

给使用者
  • 只安装你信任其后端代码的插件。安装前看一眼权限列表和源码地址，原生插件尤其要看。
  • 「允许安装未签名开发包」只影响手动安装本地文件，不会放宽商店的签名校验；测试完请关掉。
  • 更新时如果提示来源变化（仓库、发布者或签名密钥不同）或版本降级，先弄清原因再确认。
给插件作者
  • 只申请用得到的权限；能用 host.schema:read 解决的，不要申请 host.data:read。
  • 能在沙箱 UI 里完成的功能不要放进 Sidecar。只有浏览器做不到的事（TCP 协议、系统凭据、长连接、大量计算）才需要原生后端。
  • 只有真正只读的工具才标 readOnlyHint；写操作保留自己的确认流程。
  • 不要在 stdout 打日志、不要回显 Secret、不要让工具结果包含给模型的指令。

8.3写 manifest.json

把生成的 Manifest 替换为下面的内容。它声明一个工作台，以及一个挂在表右键菜单上的入口：

table-doctor/manifest.json
{
  "$schema": "https://raw.githubusercontent.com/t8y2/dbx/main/plugins/manifest.schema.json",
  "manifest_version": 1,
  "id": "com.example.table-doctor",
  "name": "Table Doctor",
  "version": "0.1.0",
  "publisher": "example",
  "description": "Inspect column metadata and null ratios of a table.",
  "icon": "assets/plugin.svg",
  "engines": { "host_api": "^1.4" },
  "permissions": ["host.schema:read", "host.data:read"],
  "entrypoints": { "ui": { "root": "ui", "entry": "ui/index.html" } },
  "contributions": [
    {
      "type": "workbench",
      "id": "com.example.table-doctor.main",
      "label": "Table Doctor",
      "icon": "assets/plugin.svg"
    },
    {
      "type": "context-menu",
      "id": "com.example.table-doctor.inspect",
      "label": "Inspect with Table Doctor",
      "menu": "table",
      "action": { "type": "open-workbench", "workbench": "com.example.table-doctor.main" }
    }
  ],
  "localizations": {
    "zh-CN": {
      "name": "表体检",
      "contributions": {
        "com.example.table-doctor.main": { "label": "表体检" },
        "com.example.table-doctor.inspect": { "label": "用表体检检查" }
      }
    }
  }
}
  • 没有 entrypoints.backend。声明了 action 的右键菜单由宿主直接打开工作台，不需要 Sidecar，最终产物是一个 universal 包。
  • menu: "table" 打开工作台时，上下文就是 TableContext：{ connectionId, database?, schema?, table }，不含主机、账号、连接串。
  • 两个权限各管一件事：getTableMetadata 需要 host.schema:read，queryData 需要 host.data:read，并且第一次查询某个连接时会弹窗征求用户同意。
  • engines.host_api 写 ^1.4，因为只读数据查询从 Host API 1.4 才有。

8.4写 ui/index.html

table-doctor/ui/index.html
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <title>Table Doctor</title>
  <style>
    body { margin: 0; padding: 16px; font: 14px/1.6 var(--font-sans, system-ui);
           background: var(--color-background, #fff); color: var(--color-foreground, #18181b); }
    .bar { display: flex; gap: 8px; align-items: center; margin-bottom: 8px; }
  </style>
</head>
<body>
  <div class="dbx-card">
    <div class="bar">
      <strong id="target">等待 DBX…</strong>
      <button id="run" class="dbx-btn dbx-btn--primary" disabled>采样 200 行</button>
    </div>
    <p id="hint" class="dbx-hint"></p>
    <table class="dbx-table">
      <thead><tr><th>列</th><th>类型</th><th>可空</th><th>样本空值率</th></tr></thead>
      <tbody id="rows"></tbody>
    </table>
  </div>
  <script>
    const $ = (id) => document.getElementById(id);
    let table = null;

    // menu: "table" 打开工作台时，context 就是 TableContext
    function onContext(context) {
      table = context && context.table ? context : null;
      $("target").textContent = table
        ? [table.database, table.schema, table.table].filter(Boolean).join(".")
        : "在侧边栏的表上右键，选「用表体检检查」";
      $("run").disabled = !table;
    }

    function cell(row, text) {
      const td = document.createElement("td");
      td.textContent = text; // 元数据和数据都按不可信文本处理
      row.append(td);
    }

    async function inspect() {
      const caps = window.dbxPlugin.capabilities || {};
      if (!caps.schemaMetadataApi || !caps.dataApi) {
        $("hint").textContent = "当前宿主不支持表元数据或数据查询";
        return;
      }
      $("hint").textContent = "读取中…";
      const { columns } = await window.dbxPlugin.getTableMetadata(table);
      // 示例没有转义标识符；正式插件应按方言引用表名
      const name = table.schema ? `${table.schema}.${table.table}` : table.table;
      const sample = await window.dbxPlugin.queryData({
        connectionId: table.connectionId,
        database: table.database,
        sql: `SELECT * FROM ${name}`,
        maxRows: 200,
      });
      const index = new Map(sample.columns.map((column, i) => [column.name, i]));
      const body = $("rows");
      body.replaceChildren();
      for (const column of columns) {
        const i = index.get(column.name);
        const nulls = i === undefined ? 0 : sample.rows.filter((row) => row[i] === null).length;
        const ratio = sample.rows.length ? Math.round((nulls / sample.rows.length) * 100) : 0;
        const tr = document.createElement("tr");
        cell(tr, column.name);
        cell(tr, column.dataType);
        cell(tr, column.nullable ? "是" : "否");
        cell(tr, `${ratio}%`);
        body.append(tr);
      }
      $("hint").textContent =
        `样本 ${sample.rows.length} 行${sample.truncated ? "（已截断）" : ""}，耗时 ${sample.elapsedMs} ms`;
    }

    window.dbxPlugin.ready.then(onContext);
    window.dbxPlugin.onContext(onContext);
    $("run").addEventListener("click", () => {
      inspect().catch((error) => { $("hint").textContent = `失败：${error.message}`; });
    });
  </script>
</body>
</html>
  • 页面用 DBX 注入的 --color-*、--font-sans 变量和 dbx-card、dbx-btn、dbx-table 样式，自动跟随浅色、深色主题。
  • 先读 capabilities 再调用，旧版 DBX 上会显示提示而不是报错。
  • 所有外部数据都用 textContent 写入页面。表名、列名和单元格都来自数据库，不要拼进 innerHTML。
  • 用户拒绝数据访问时 queryData 会 reject，catch 把原因显示出来，用户可以再点一次重新授权。

use std::sync::Mutex;

use dbx_plugin_sdk::{PluginEmitter, PluginError, PluginHandler, PluginMetadata, PluginServer, RequestContext};
use serde_json::{json, Value};

#[derive(Default)]
struct Plugin {
    connections: Mutex<HashSet<String>>,
}

impl PluginHandler for Plugin {
    fn handle(&self, _ctx: RequestContext, method: &str, params: Value, emitter: &PluginEmitter)
        -> Result<Value, PluginError> {
        match method {
            "connection/test" => Ok(json!({ "success": true, "message": "Ready" })),
            "connection/connect" => {
                let id = connection_id(&params)?;
                self.connections.lock().map_err(|_| PluginError::new(-32000, "poisoned"))?.insert(id.to_string());
                emitter.event("demo/connectionChanged", json!({ "connectionId": id, "state": "connected" }))?;
                Ok(json!({ "success": true }))
            }
            "connection/disconnect" => {
                let id = connection_id(&params)?;
                self.connections.lock().map_err(|_| PluginError::new(-32000, "poisoned"))?.remove(id);
                Ok(json!({ "success": true })) // 幂等：重复断开也返回成功
            }
            "demo/ping" => Ok(json!({ "ok": true })),
            _ => Err(PluginError::method_not_found(method)),
        }
    }
}

fn connection_id(params: &Value) -> Result<&str, PluginError> {
    params
        .pointer("/connection/id")
        .and_then(Value::as_str)
        .ok_or_else(|| PluginError::new(-32602, "Missing connection id"))
}

fn main() -> std::io::Result<()> {
    // ID 与版本必须和 manifest.json 完全一致，否则握手失败
    let metadata = PluginMetadata::new("com.example.demo", env!("CARGO_PKG_VERSION"))
        .with_capability("connections")
        .with_capability("events");
    PluginServer::new(metadata, Plugin::default()).serve()
}

8.8提交到官方商店

  1. 发布候选包。推送源码，打版本 Tag 并发布 GitHub Release。生成项目自带的 plugin-release.yml 调用 t8y2/dbx 的可复用工作流（锁定工作流 commit 与 plugin-cli-version），按平台构建未签名候选包，上传每个 .dbxp、.artifact.json 和合并后的 release-candidates.json。工作流会拒绝带 signature.json 或 signingKeyId 的候选包。
  2. 开候选 PR。首次上架时 fork t8y2/dbx-store，向 main 提一个 PR，包含 publishers/<publisher-id>.json 和 candidates/<plugin-id>.json，不需要先开 Issue。仓库登记到 automation/plugin-sources.json 并设置 autoUpdate: true 后，之后的每个版本都由同步机器人自动开 PR。
  3. 等待审核。CI 会一直报 open candidate(s) awaiting DBX Store signing，这是有意阻止合并未签名内容。维护者检查源码、Manifest、权限、候选包的哈希与大小以及原生行为。
  4. 签名并合并。维护者在 PR 下评论 /sign，受保护的工作流签名、发布到 R2，把 plugins/<id>.json 和 catalog/index.json 写回同一个 PR。CI 变绿后合并，插件出现在所有 DBX 的插件中心。

上架 PR 里不要放
  • .dbxp 二进制或插件源码副本；
  • 私钥、Token、下载凭据；
  • 未签名候选包的地址作为最终下载地址，或自行填写的 signingKeyId；
  • 自己设置的 verified: true，这个标记只由维护者决定。

更新插件时，每次都递增 manifest.json 的 version，发布新的 Tag 和候选 Release。已发布的资产不能覆盖，任何字节变化都要走一个新版本。插件代码的问题在插件仓库修；只有目录信息、下载地址、哈希、大小和商店文案的变化才进 dbx-store。

术语表

宿主 Host
DBX 本身。负责安装、启动、隔离插件，并替插件做受控的事。
Sidecar
插件的原生后端进程，经 stdin/stdout 与宿主通信，以当前用户权限运行。
工作台 Workbench
在 DBX 标签页中打开的沙箱 iframe，承载插件 UI。
贡献点 Contribution
Manifest 中声明的界面挂载点，共八种。
Host API
宿主开放给插件的能力集合，当前 1.4.0，按次版本递增。
候选包 Candidate
作者 CI 产出的未签名 .dbxp，只用于审核，不能直接从商店安装。
仓库签名
分发仓库在审核后对包做的 Ed25519 签名，证明字节未被替换，不代表代码无害。
Key ID
仓库签名公钥的稳定公开标识，例如 dbx-store-release-2026。轮换时启用新 ID，旧 ID 不复用。
激活记录
activations/ 下按序号递增的 JSON，决定当前版本、回滚目标，并记录包哈希与来源。
来源 Provenance
安装时记录的仓库、发布者、签名 Key ID 与安装方式，用于检查更新连续性。
target
包的目标平台，如 darwin-arm64；universal 表示同一个包适用于所有平台。
TableContext
表级入口传给插件的对象身份：connectionId、可选的 database 与 schema、table，不含凭据。
